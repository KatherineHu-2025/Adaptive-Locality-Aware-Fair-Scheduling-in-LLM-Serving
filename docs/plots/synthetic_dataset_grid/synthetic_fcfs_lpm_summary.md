## Next Step: Real-Trace Runs (Chatbot Arena / LooGLE)

The benchmark driver now supports real-trace datasets via `--dataset`.

Important note for non-synthetic datasets:
- `--request-counts` is interpreted as `--max-reqs` passed to `workload.client`.
- `dominant_reqs` / `cold_reqs` are only meaningful for `synthetic`.

Recommended focused sweep (fast, high signal):
- Rates: `1.0,2.0,3.0`
- k values: `0.5,1.0`
- Request counts: `30`
- Arrival mode: `per-client`

Why these specific values:
- Rates `1.0,2.0,3.0` cover moderate to high load where scheduler differences are most visible, while avoiding very low-load runs that can be noisy/outlier-prone.
- `k=0.5` captures bursty arrivals and `k=1.0` is the Poisson baseline; this pair gives the highest signal per run for fairness-vs-locality tradeoffs.
- `k=2.0` (smoother arrivals) is useful, but intentionally deferred to a second pass if needed to save runtime.

### Chatbot Arena (fairness-focused pass)

Rationale for this subset on Chatbot Arena:
- Start with `rate=1,2,3` and `k=0.5,1.0` to quickly identify policy ordering under bursty and baseline traffic.
- Expand to `k=2.0` or add more rates only after the first pass shows where curves diverge.

## Gamma k Clarification

`k` matters for all positive values, not only when `k < 1`.

With Gamma inter-arrival and fixed rate:
- `k < 1`: burstier arrivals (high variance)
- `k = 1`: Poisson/exponential arrivals
- `k > 1`: more regular/smoother arrivals (lower variance)

So your understanding is partially right: `k < 1` is where burstiness becomes pronounced, but `k > 1` is still useful because it gives a distinct arrival regime (smoother traffic) and helps test scheduler behavior under lower burst noise.

If runtime is tight, prioritize `k=0.5` and `k=1.0`. Add `k=2.0` only for a smaller second pass.
