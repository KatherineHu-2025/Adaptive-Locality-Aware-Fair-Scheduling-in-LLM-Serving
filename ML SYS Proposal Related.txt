The Core Reason: We Need to Read the Radix Tree
Our entire scheduler depends on one operation at each scheduling step:
"For this waiting request, how many of its prefix tokens are already cached?"
That requires querying a live radix tree that reflects the current cache state. The two systems differ fundamentally in how they expose this.

SGLang
RadixAttention was invented by the SGLang team (the SGLang paper, 2024). So the radix tree is not a plugin or an afterthought — it is the core data structure of the cache manager. Concretely:
* The radix tree is always on, always maintained, and always consistent with the physical KV blocks
* There is a clean prefix_match(tokens) → cached_length API already exposed internally
* The scheduler and the cache manager are in the same process, sharing the same in-memory tree — so a cache score lookup is just a Python function call, no IPC, no serialization
For our project, computing cache_score(r) is essentially already implemented — we just need to call the existing prefix match at scheduling time and use the result to reorder the queue.
________________


vLLM
vLLM has prefix caching (added in v0.2+), but it works differently from RadixAttention in ways that matter for us:
* vLLM's prefix cache uses a hash map keyed on token block hashes, not a radix tree. There is no tree to walk — you check if a block-aligned prefix chunk is cached, but you don't get a smooth "how many tokens are cached" signal. You get block-level granularity (e.g., blocks of 16 tokens), which is coarser.
* The prefix cache is more tightly coupled to the block allocator, and less exposed as a queryable API at the scheduler layer. Accessing it from the scheduler requires reaching into lower-level internals.
* vLLM's scheduler was designed around FCFS + preemption and has less modularity for injecting a custom priority function without deeper refactoring.
In short, in vLLM you'd have to build the thing we're trying to use, whereas in SGLang it already exists.

The Key Distinction: LPM for Cache Reuse vs. LPM for Scheduling Decisions
SGLang's existing LPM does one thing: when a request is already selected to run, find and reuse whatever prefix is cached.
The order is:
Scheduler picks request → THEN radix tree does LPM → reuse whatever is cached
Our contribution flips the dependency:
Radix tree does LPM on ALL waiting requests → THEN scheduler uses those scores to decide WHO to pick
SGLang's LPM is reactive — it fires after the scheduling decision is already made. Our scheduler makes LPM proactive — a first-class input to the scheduling decision itself.
________________


A Concrete Example of Why This Matters
Say the batch has one open slot, and three requests are waiting:
Request A: cache_score = 0.05  (cold, arrived 10ms ago)
Request B: cache_score = 0.97  (hot, arrived 8ms ago)  
Request C: cache_score = 0.12  (cold, arrived 5ms ago)
What SGLang's existing scheduler does: Picks A — it arrived first. Then LPM runs on A, finds 5% cached, runs expensive prefill on the rest. B and C wait. The fact that B was nearly free to serve is invisible to the scheduler.
What our scheduler does: Picks B — highest cache score, saves ~95% of prefill compute. A and C wait a little longer, but overall system throughput improves.
SGLang's LPM would have given B the same cache reuse if it had been selected — but it never was, because the scheduler didn't know to prefer it.

The Analogy
Think of a supermarket checkout. SGLang's current behavior is like a cashier who processes whoever is next in line, and happens to scan their items quickly if they have fewer items. Our scheduler is like a cashier who looks down the whole line, spots the person with 2 items, and calls them forward — reducing total checkout time for everyone.
The scanning speed (LPM / cache reuse) is the same in both cases. The difference is who gets called to the register.

Claude’s response on if LPM starvation is a real problem and is PAS-D a possible direction to solve it

The LPM starvation problem is a real, actively researched issue — not yet fully solved, but several mitigations exist. Let me break this down precisely.
________________


What is LPM and why does it cause starvation?
In SGLang's RadixAttention, the default scheduling policy is Longest Prefix Match (LPM): at each scheduling step, the scheduler greedily picks the waiting request that shares the longest cached prefix with the current radix tree. This maximizes KV cache reuse and improves throughput — in the offline setting (all queries known upfront), LPM is theoretically optimal for cache reuse.
The problem emerges in online, heavy-traffic settings. LPM is greedy and myopic: it repeatedly favors requests that match popular cached prefixes, while requests with mismatching or rare prefixes can sit in the queue indefinitely. Existing scheduling approaches like LPM can lead to large TTFT (time-to-first-token) spikes under heavy traffic arXiv, because a request unlucky enough to not match a hot prefix keeps getting deprioritized as new matching requests keep arriving.
This is the classic starvation problem from OS scheduling, now reborn in LLM serving.
There's also a related but distinct fairness problem: LPM fails to guarantee effective isolation among clients — a malicious or high-volume client can monopolize shared resources by sending a large number of requests with long identical prefixes, significantly degrading the performance experienced by other clients. arXiv

Is it solved?
Not fully. Here's the state of things:
Theoretically: The scheduling problem with prefix reuse under TTFT constraints has been proven NP-hard. arXiv So you can't have a polynomial-time algorithm that's both optimal for cache reuse AND guarantees deadline/latency compliance simultaneously.
Practically, several mitigations exist:
1. k-LPM (arxiv 2502.04677, Feb 2025) — proposes a family of algorithms parameterized by k, where k=1 recovers LPM and k=∞ approaches FCFS. The goal is to exploit the benefits of LPM but mitigate its performance risks in high-load scenarios, resulting in superior performance for long-prompt, short-output queries where RadixAttention delivers significant efficiency gains. arXiv It essentially limits how aggressively the scheduler can deprioritize waiting requests.
2. D2LPM / Locality-aware Fair Scheduling (arxiv 2501.14312, Jan 2025) — addresses the fairness angle. Preble performs slightly better than vanilla LPM due to its multi-level priority wait queue, which avoids starvation but cannot provide isolation and strict fairness guarantees. arXiv D2LPM improves on this by explicitly optimizing for prefix locality while maintaining client fairness bounds.
3. VTC (Virtual Token Clock) — a fairness-first scheduler that prevents starvation but sacrifices locality/cache hit rate. Good for multi-tenant scenarios with strict isolation requirements.
4. Decode priority scheduling — both vLLM and SGLang already prioritize running decode requests over new prefills, which helps with a different starvation scenario (decode requests being starved by large prefill bursts).
________________


Can PAS-D (deadline-aware / slot-holding) be implemented in SGLang?
PAS-D isn't a widely published acronym in this exact form in the LLM serving literature — you may be referring to a deadline-aware scheduling policy akin to EDF (Earliest Deadline First) with slot reservation. The concept maps cleanly onto the k-LPM / aging approach. Here's how you'd implement it:
The core idea would be: each waiting request is assigned a soft deadline based on its arrival time and an SLO target (e.g., TTFT ≤ 2s). A slot is reserved for it in the batch once its deadline approaches. The scheduler normally runs LPM, but any request within some threshold of its deadline gets deadline-promoted into the next batch regardless of prefix match length.
Here's a sketch of how this would plug into SGLang's scheduler:
python
# SGLang scheduler hook (simplified)
class DeadlineAwareLPMScheduler:
    def __init__(self, deadline_slo_ms=2000, promotion_threshold_ms=500):
        self.deadline_slo = deadline_slo_ms
        self.promotion_threshold = promotion_threshold_ms


    def get_next_batch(self, waiting_queue, radix_tree, current_time):
        # Step 1: identify deadline-critical requests
        promoted = [
            req for req in waiting_queue
            if (current_time - req.arrival_time) >= 
               (self.deadline_slo - self.promotion_threshold)
        ]


        # Step 2: fill remaining slots with LPM
        remaining_budget = MAX_BATCH_SIZE - len(promoted)
        lpm_sorted = sorted(
            [r for r in waiting_queue if r not in promoted],
            key=lambda r: radix_tree.longest_prefix_match(r.tokens),
            reverse=True
        )


        return promoted + lpm_sorted[:remaining_budget]
Challenges in SGLang specifically:
The SGLang scheduler runs in a tight overlapped loop (the zero-overhead scheduling from your lecture notes — run_batch and process_batch_result are interleaved). Injecting deadline logic has to be careful not to break the non-blocking contract. The right place to hook in is get_next_batch_to_run() in the scheduler. SGLang's RadixCache already exposes prefix length matching via the radix tree, so the LPM side is easy to intercept.
The k-LPM paper's approach is essentially this but formalized: it uses an "aging" parameter where a request's effective priority is prefix_match_length - α * wait_time, allowing you to tune the starvation-vs-reuse tradeoff with a single knob. That's probably the cleanest way to implement PAS-D semantics in SGLang.
Bottom line: LPM starvation is a genuine, theoretically hard problem that isn't fully solved. The research community is actively working on it (multiple papers in 2025). SGLang's architecture is amenable to deadline-aware extensions — the scheduler is Python-level and the radix tree is exposed. The k-LPM framework gives you the cleanest theoretical grounding for implementing a PAS-D-style policy.

Existing Research on LLM Scheduling & Starvation
The academic community has just started publishing heavily on this exact problem within the last year. Here are three excellent papers you can reference in your proposal that validate your approach to solving the starvation vs. prefix-hit-rate tradeoff:
1. "Locality-aware Fair Scheduling in LLM Serving" (January 2026)

Gemini’s Response to “does DLPM adapt well to changes in workloads? Do they have parameters that they tune/adapt throughout online serving, and could that be an area that we talk about where we hope to improve it?”
This is a brilliant insight and an excellent angle for your proposal. You have identified the exact limitation of DLPM that makes it ripe for improvement in a systems project.
Here are the answers to your questions based on the DLPM paper, and how you can frame this as the core contribution of your project:
1. Does DLPM adapt well to changes in workloads?
DLPM is designed to handle diverse workloads structurally (by tracking deficits to prevent strict starvation), but it does not adapt its underlying policy dynamically when the traffic distribution changes. If a system suddenly transitions from a period of highly homogeneous requests (where maximizing locality is safe and efficient) to a period of highly heterogeneous, disjoint requests (where starvation becomes a massive risk), DLPM's static configuration might struggle to find the optimal balance point.
2. Do they have parameters that they tune throughout online serving?
No, they do not. The core mechanism of DLPM relies on a hyperparameter Q (often referred to as the quantum or relaxation bound).
* Q controls how much the scheduler is allowed to "relax" the fairness constraint in order to chase longest prefix matches.
* A small Q enforces strict fairness (behaving closer to VTC).
* A large Q heavily prioritizes locality and throughput (behaving closer to pure LPM).
In the paper, the authors treat Q as a static hyperparameter. They evaluate different fixed values (e.g., Q=1000, Q=2000, Q=8000, Q=32000) to demonstrate a Pareto frontier between throughput and fairness, but they do not propose any mechanism to automatically tune Q during online serving.
3. How to use this in your proposal
This is exactly where your team can introduce a major improvement. In the real world, production LLM traffic is bursty and diurnal; a static Q that works perfectly at 2:00 PM might cause unacceptable tail latency at 8:00 PM.
You can explicitly update the Problem and High-level implementation plans sections of your proposal to include an Adaptive Fairness Policy. Here is how you could phrase it:
Addition to the Problem Statement:
While DLPM successfully balances fairness and locality, it relies on a statically configured relaxation hyperparameter (Q). Under rapidly fluctuating online workloads, a static parameter cannot optimally navigate the Pareto frontier, either over-penalizing throughput during homogeneous traffic bursts or under-penalizing starvation during diverse traffic spikes. We ask: Can we design an adaptive scheduler that dynamically tunes the fairness-locality tradeoff at runtime based on real-time queue states?
Addition to the Implementation Plan:
* Adaptive Policy Controller: Implement a feedback loop in mini SGLang that monitors real-time system metrics (e.g., maximum request waiting time, queue depth, or prefix cache hit rate).
* Dynamic Adjustment: If the P99 waiting time exceeds a specific Service-Level Objective (SLO), the scheduler dynamically tightens the fairness bound (equivalent to lowering Q). Conversely, if queue latency is healthy, the scheduler relaxes the bound to maximize prefix cache utilization and system throughput.
Framing your project around an "Adaptive-DLPM" or an "Auto-Tuning Fairness Scheduler" elevates it from a simple re-implementation to a novel systems contribution. It perfectly bridges the gap between efficiency and practical, real-world deployment!

[b]Existing schedulers for serving face a starvation issue as the LPM policy uses a greedy approach that only makes decisions purely based on prefix cache score
-> LPM maximizes locality and throughput but enables a dominant or malicious client with long shared prefixes to monopolize the GPU, starving other clients
Some requests might not be scheduled for a long time (for ex new requests) if their context aren’t in the prefix cache 
With the rise of multi-turn agentic workflows and massive system prompts, the penalty for a prefix cache miss and the resulting starvation is much more severe now. 
In a multi-tenant LLM serving system, starvation disproportionately affects clients whose requests have little or no overlap with what is currently cached in the prefix tree — most notably, a brand-new client sending their first request, or any client switching to a new topic. Because LPM greedily schedules requests with the longest matching prefix, these "cold" requests are perpetually deprioritized whenever a dominant client is flooding the system with requests that share a long common prefix.
Why fairness matters: This is particularly problematic in shared API settings, where multiple users or organizations are concurrent clients on the same infrastructure. Each client expects predictable, isolated performance — their latency should not degrade simply because another client happens to have a cache-friendly workload or behaves maliciously by sending large volumes of prefix-heavy requests to monopolize the GPU.
